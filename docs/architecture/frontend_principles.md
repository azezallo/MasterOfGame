# Принципи архітектури UI

Цей документ визначає стандарти розробки фронтенд-частини проєкту Master of Game. Наша мета — створити швидкий, реактивний та портативний інтерфейс з мінімальним використанням зовнішніх бібліотек.

## Основні принципи

### 1. Feature-Based Architecture (Структура папок)
Ми використовуємо підхід, де код організований навколо фіч, а не типів файлів. Це дозволяє ізолювати логіку та полегшує масштабування:

*   **src/**
    *   **app/** — Глобальні налаштування (провайдери, глобальні стилі, роутинг).
    *   **components/** — UI-компоненти загального призначення (Button, Input, Modal, Loader).
    *   **hooks/** — Глобальні перевикористовувані хуки (useAuth, useTheme, useDebounce).
    *   **services/** — Базовий API-клієнт, робота з LocalStorage, конфігурація WebSockets.
    *   **utils/** — Допоміжні чисті функції (форматування дат, математичні розрахунки).
    *   **features/** — Ізольовані бізнес-модулі додатка.
        *   **auth/** — Приклад фічі: авторизація користувача.
        *   **character/** — Приклад фічі: керування ігровим персонажем.
            *   **api/** — Специфічні для цієї фічі запити до бекенду.
            - **components/** — Компоненти, які використовуються виключно в цій фічі.
            - **hooks/** — Локальні хуки (ізольована бізнес-логіка фічі).
            - **types/** — TypeScript інтерфейси та Zod-схеми валідації.
            - **index.ts/** — Public API фічі (експортує лише те, що потрібно іншим модулям).

### 2. Шари всередині бізнес-модуля (Feature Layers)
Для дотримання принципу розділення відповідальності (Separation of Concerns), код всередині кожної фічі розділений на чотири архітектурні шари:

#### Presentation Layer (UI Components)
- **Роль**: Відображення інтерфейсу та взаємодія з користувачем.
- **Відповідальність**:
    - Рендеринг HTML/JSX елементів.
    - Стилізація компонентів.
    - Виклик функцій-колбеків при тригерах від користувача (click, submit, change).
- **Заборонено**: Містити прямі запити до API (fetch/axios), складну бізнес-логіку або пряму трансформацію сирих даних з бекенду. Компонент має бути максимально "дурним" (Dumb Component) і отримувати готові дані/обробники через пропси або локальні хуки.

#### Logic Layer (Custom Hooks)
- **Роль**: "Мозок" компонентів фічі (аналог Service Layer на бекенді).
- **Відповідальність**:
    - Керування локальним станом (`useState`, `useReducer`).
    - Обробка подій, маніпуляція даними та валідація форм (використання React Hook Form + Zod).
    - Координація між глобальним стайтом та сервісами запитів.
- **Заборонено**: Маніпулювати DOM-деревом напряму чи містити JSX-розмітку. Хук повертає виключно чисті дані, стани та функції-обробники для UI.

#### API & Data Access Layer (Services / Client)
- **Роль**: Абстракція мережевих запитів.
- **Відповідальність**:
    - Виконання HTTP/WebSocket запитів до `master_of_game_API`.
    - Мапінг та трансформація даних з бекенду у зручний для фронтенду формат (DTO -> Domain Model).
    - Ізоляція методів `fetch` або `axios` в окремі чисті функції.
- **Заборонено**: Зберігати стан UI або знати про те, який саме компонент викликає цей запит.

#### Domain Models & Types
- **Роль**: Опис бізнес-сутностей.
- **Відповідальність**:
    - Опис TypeScript інтерфейсів фронтенд-моделей (наприклад, `Player`, `InventoryItem`).
    - Створення Zod-схем для валідації відповідей від API (захист рантайму від непередбачуваних змін на бекенді).

### 3. Технічні вимоги

#### Управління станом (State Management)
- **Локальний стейт**: Використовувати локальні стейти (React `useState`, `useReducer`) як основний механізм для більшості компонентів.
- **Глобальний стейт**: Використовувати лише для дій, що мають глобальний охоп (наприклад, стан авторизації, загальні налаштування).
- **Чистота даних**: Використовувати однонаправлений потік даних (one-way data flow).

#### Компоненти та стилізація
   - **CSS Modules**: Використовувати CSS Modules як основний метод стилізації для забезпечення ізоляції стилів та високої продуктивності.
   - **Компонентний підхід**: Розділяти UI на примітивні (Buttons, Inputs), молекулярні (SearchInput, Card) та організмні (Header, LoginForm) компоненти.
   - **Реузабельність**: Кожен компонент має бути незалежним. Якщо компонент використовується більше ніж у двох місцях, він повинен бути винесений у спільну бібліотеку компонентів.
   - **Путеві шляхи (Import Standards)**:
       - Базові UI компоненти: `@/src/components/ui/`
       - Глобальні хуки: `@/src/hooks/`
       - Спільні сервіси: `@/src/services/` або `@/src/api/`
       - Контексти: `@/src/context/`
       - Використовувати відносні шляхи для внутрішніх компонентів фічі, але глобальні шляхи для спільних ресурсів.
       - Заборонено додавати розширення файлів (наприклад, `.tsx`, `.ts`) в імпортах.

### 4. Інтеграція з API та UX
- **Обробка станів завантаження**: Обов'язкова візуальна обробка станів завантаження (Skeletons або Spinners) для всіх асинхронних запитів.
- **Оптимізація запитів**: Використовувати стандартні методи `fetch` або `axios`, забезпечуючи чітко визначені інтерфейси відповідей від бекенду.

### 5. Адаптивність та доступність
- **Мобільна підтримка**: Гра повинна повноцінно працювати на мобільних пристроях. Пріоритет надається адаптивності під різні екрани.
- **Інтерфейс**: Створити інтуїтивно зрозумілий інтерфейс, що підходить як для мишки, так і для сенсорного керування.

## Технічні вимоги

### 1. Типобезпека (TypeScript)
- Використовувати суворий режим TypeScript.
- Використовувати Zod для валідації даних на рівні компонентів, де це необхідно.

### 2. Код-стайл
- Чистий та читабельний код.
- Мінімальне використання сторонніх бібліотек (використовувати нативні можливості React та браузера).
- Чіткий розподіл відповідальності між компонентами презентації та контейнерами.

### 3. Локалізація (i18n)
- **Підхід**: Увесь інтерфейсний текст повинен виноситися у JSON-файли локалізації (`src/i18n/locales/uk.json`).
- **Хуки**: Використовувати нативний хук `useTranslation()` з бібліотеки `react-i18next`.
- **Заборона захардкоджених стрічок**: Забороняється захардкоджувати у відкритому вигляді текстові рядки безпосередньо у JSX компонентів (наприклад, замість `<h3>Стан</h3>` використовувати `<h3>{t('player_state.title')}</h3>`).
