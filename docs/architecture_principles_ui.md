# Архітектурні принципи та Best Practices (Frontend)

Цей документ визначає стандартні підходи до розробки клієнтської частини `master_of_game_UI` на базі чистого React + TypeScript (без використання фреймворків).

## Архітектурна модель: Feature-Based / Layered Architecture

Для забезпечення масштабованості, ізоляції та чистоти коду додаток ділиться на **модулі (features)**, кожен з яких має чітку шарову структуру. Це дозволяє уникнути хаосу в глобальних папках та спрощує паралельну розробку.

## Структура папки додатка (`src/`)

* **src/**
  * **app/** — Глобальні налаштування (провайдери, глобальні стилі, роутинг)
  * **components/** — UI-компоненти загального призначення (Button, Input, Modal, Loader)
  * **hooks/** — Глобальні перевикористовувані хуки (useAuth, useTheme, useDebounce)
  * **services/** — Базовий API-клієнт, робота з LocalStorage, конфігурація WebSockets
  * **utils/** — Допоміжні чисті функції (форматування дат, математичні розрахунки)
  * **features/** — Ізольовані бізнес-модулі додатка
    * **auth/** — Приклад фічі: авторизація користувача
    * **character/** — Приклад фічі: керування ігровим персонажем
      * **api/** — Специфічні для цієї фічі запити до бекенду
      * **components/** — Компоненти, які використовуються виключно в цій фічі
      * **hooks/** — Локальні хуки (ізольована бізнес-логіка фічі)
      * **types/** — TypeScript інтерфейси та Zod-схеми валідації
      * **index.ts/** — Public API фічі (експортує лише те, що потрібно іншим модулям)

## Шари всередині бізнес-модуля (Feature Layers)

Для дотримання принципу розділення відповідальності (Separation of Concerns), код всередині кожної фічі розділений на чотири архітектурних шари:

### 1. Presentation Layer (UI Components)
- **Роль**: Відображення інтерфейсу та взаємодія з користувачем.
- **Відповідальність**:
    - Рендеринг HTML/JSX елементів.
    - Стилізація компонентів.
    - Виклик функцій-колбеків при тригерах від користувача (click, submit, change).
- **Заборонено**: Містити прямі запити до API (fetch/axios), складну бізнес-логіку або пряму трансформацію сирих даних з бекенду. Компонент має бути максимально "дурним" (Dumb Component) і отримувати готові дані/обробники через пропси або локальні хуки.

### 2. Logic Layer (Custom Hooks)
- **Роль**: "Мозок" компонентів фічі (аналог Service Layer на бекенді).
- **Відповідальність**:
    - Керування локальним станом (`useState`, `useReducer`).
    - Обробка подій, маніпуляція даними та валідація форм (використання React Hook Form + Zod).
    - Координація між глобальним стейтом та сервісами запитів.
- **Заборонено**: Маніпулювати DOM-деревом напряму чи містити JSX-розмітку. Хук повертає виключно чисті дані, стани та функції-обробники для UI.

### 3. API & Data Access Layer (Services / Client)
- **Роль**: Абстракція мережевих запитів.
- **Відповідальність**:
    - Виконання HTTP/WebSocket запитів до `master_of_game_API`.
    - Мапінг та трансформація даних з бекенду у зручний для фронтенду формат (DTO -> Domain Model).
    - Ізоляція методів `fetch` або `axios` в окремі чисті функції.
- **Заборонено**: Зберігати стан UI або знати про те, який саме компонент викликає цей запит.

### 4. Domain Models & Types
- **Роль**: Опис бізнес-сутностей.
- **Відповідальність**:
    - Опис TypeScript інтерфейсів фронтенд-моделей (наприклад, `Player`, `InventoryItem`).
    - Створення Zod-схем для валідації відповідей від API (захист рантайму від непередбачуваних змін на бекенді).

## Best Practices

### 1. State Management (Керування станом)
- **Локальний стан**: Використовувати `useState` або `useReducer` максимально близько до місця використання. Не виносити в глобальний стейт те, що потрібно лише одному компоненту чи формі.
- **Глобальний стан**: Для базових, рідко змінюваних даних (тема, мова, сесія користувача) використовувати **React Context**. Для динамічного ігрового стану, який часто оновлюється, використовувати легкі стейт-менеджери з атомарними оновленнями (наприклад, **Zustand**), щоб уникнути зайвих ререндерів.
- **Серверний стан**: Замість самописних `useEffect` для завантаження даних, використовувати **TanStack Query (React Query)**. Він бере на себе кешування, автоматичне оновлення, обробку помилок та менеджмент станів завантаження (`isLoading`, `isError`).

### 2. Type Safety & Runtime Validation
- Обов'язкове використання сувого режиму TypeScript (`strict: true`).
- **Валідація рантайму**: Оскільки структура даних на бекенді може змінитися без відома фронтенду, критичні відповіді від API рекомендується валідувати через `Zod` безпосередньо в шарі запитів.

### 3. Error Handling & Boundaries
- Використання **React Error Boundaries** (Границі помилок) для ізоляції runtime-помилок у компонентах, щоб вихід з ладу одного віджета не руйнував весь інтерфейс додатку.
- Створення універсальних UI-заглушок (Fallback components) для інформування користувача про помилку.

### 4. Performance & Rendering
- **Оптимізація обчислень**: Використовувати `useMemo` та `useCallback` свідомо — лише для важких математичних розрахунків або для збереження посилальної цілісності об'єктів/функцій, які передаються в оптимізовані дочірні компоненти (`React.memo`).
- **Розділення коду (Code Splitting)**: Використання `React.lazy` та `Suspense` для динамічного завантаження великих сторінок або важких ізольованих модулів (наприклад, сторінки "Адмін-панель" чи "Аналітика").

### 5. Code Style & Component Architecture
- **Принцип єдиної відповідальності (SRP)**: Один компонент виконує одне завдання. Якщо файл компонента розростається понад 150–200 рядків, його логіку необхідно винести в кастомний хук, а JSX розділити на менші підкомпоненти.
- **Ізоляція через Public API**: Кожна папка у `features/` повинна мати файл `index.ts`. Будь-які інші модулі додатку можуть імпортувати сутності з цієї фічі **виключно** через цей індексний файл. Глибокі імпорти (наприклад, `import { Button } from '@/features/auth/components/Button'`) суворо заборонені.
