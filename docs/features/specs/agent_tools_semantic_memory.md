# Специфікація: Семантична пам'ять та RAG (F017)

Цей документ описує архітектуру довгострокової пам'яті (Long-Term Memory) та конвеєр Retrieval-Augmented Generation (RAG) для ШІ-Майстра. Мета — забезпечити Майстра контекстом про глибоке минуле гри чи правила світу, не перевантажуючи контекстне вікно LLM.

## 1. Архітектура та Технології

Щоб мінімізувати навантаження на систему (особливо на відеокарту, яка буде зайнята основною LLM) і уникнути необхідності піднімати окремі сервіси (як-от Docker-контейнери з ChromaDB чи Qdrant), система використовує повністю вбудований у Node.js стек.

### 1.1. База Даних (SQLite + Vector Search)
Усі дані (як звичайні реляційні таблиці, так і векторні) зберігаються в єдиній локальній базі даних.
- **Драйвер:** `better-sqlite3` (вже використовується в `master_of_game_API`).
- **Векторне розширення:** `sqlite-vec` (або `sqlite-vss`). `sqlite-vec` є сучасним, надзвичайно легким розширенням, написаним на C, яке ідеально інтегрується з `better-sqlite3` і дозволяє зберігати масиви `Float32Array` та робити швидкий пошук за косинусною відстанню.
- **Перевага:** Немає мережевих затримок, бекап всієї гри (включно з пам'яттю) — це просто копіювання одного файлу `.sqlite`.

### 1.2. Генерація Ембеддингів (Embedding Model)
Щоб не забирати VRAM у основної моделі, векторизація тексту відбувається виключно на процесорі (CPU) всередині Node.js процесу.
- **Бібліотека:** `fastembed-js` або `@xenova/transformers` (HuggingFace Transformers для JavaScript).
- **Модель:** Легковагова модель для генерації ембеддингів (наприклад, `BGE-small` або `all-MiniLM-L6-v2`). Ці моделі займають ~100 МБ оперативної пам'яті, швидко працюють на CPU і дають достатню якість семантичного пошуку.
- **Процес:** Коли бекенд зберігає новий "Стиснений сухий лог", він передає цей текст у бібліотеку ембеддингів на CPU. Отриманий вектор записується в `sqlite-vec`. Оскільки текстів небагато (лише стислі факти), навантаження на CPU буде непомітним.

## 2. Схема Даних (Vector DB Schema)

Векторна таблиця історії зберігається у SQLite і містить не лише сухі факти, а й точні репліки Майстра та гравця, оскільки точність формулювань критично важлива для семантичного пошуку.

### 2.1. Структура Таблиці `semantic_history`
- `id` (Primary Key, UUID або Integer) — унікальний ідентифікатор запису.
- `turn_number` (Integer) — номер ходу в межах поточної гри. Дозволяє сортувати знайдену пам'ять хронологічно або фільтрувати події за віком (наприклад, "тільки події до 100 ходу").
- `role` (String/Enum) — джерело або тип повідомлення. Значення:
  - `player` (пряма мова або дія гравця).
  - `master` (точна художня відповідь Майстра).
  - `system` (стислий сухий факт, лог або результат роботи Сабагента).
- `content` (Text) — безпосередньо текст повідомлення. Саме цей текст передається в embedding-модель.
- `embedding` (Vector / Float32Array) — багатовимірний вектор для `content`, що дозволяє швидкий пошук за косинусною відстанню через `sqlite-vec`.
- `tags` (JSON Array) — набір метаданих для гібридного пошуку. Дозволяє базі відсіяти зайве ще до математичного порівняння векторів. Приклад: `["location:city", "npc:guard_captain"]`.
- `world_time` (String/ISO Date) — поточний внутрішньоігровий час (стандартний об'єкт Date у форматі ISO 8601). Оскільки між ходами в грі може пройти як 5 хвилин, так і 5 місяців, цей параметр дозволяє шукати і фільтрувати події саме за точним часом світу гри.
- `created_at` (Timestamp) — точний реальний час створення запису.

## 3. Агентний інструмент пошуку (`search_memory`)

Цей інструмент призначений для цілеспрямованого пошуку в довгостроковій пам'яті. Майстер (або Сабагент за його вказівкою) може викликати цей тул під час Re-Act циклу, щоб дістати потрібні факти минулого.

### 3.1. Схема виклику (Input Parameters)
- `query` *(String, Required)*: Текстовий запит для семантичного векторного пошуку (напр., "Де захований медальйон?").
- `tags_filter` *(Array of Strings, Optional)*: Теги для звуження пошуку (напр., `["location:cave"]`).
- `role_filter` *(String, Optional)*: Пошук виключно по словах гравця, Майстра або системних логах (`player`, `master`, `system`).
- `world_time_range` *(Object, Optional)*: Діапазон ігрового часу у форматі ISO (напр. `{ "start": "1284-05-12T14:00:00.000Z", "end": "1284-05-15T14:00:00.000Z" }`). Дозволяє Майстру шукати події, що відбулися в конкретний часовий проміжок світу.

### 3.2. Обмеження та Результат (Output)
Щоб гарантовано не переповнити залишкове контекстне вікно моделі, інструмент на рівні бекенду **завжди** повертає жорстко обмежений масив (максимум 3 результати) найрелевантніших записів:
```json
[
  { 
    "turn": 45, 
    "world_time": "Day 12, 14:00",
    "role": "player", 
    "content": "Я ховаю медальйон під старим дубом біля печери." 
  },
  { 
    "turn": 46, 
    "world_time": "1284-05-12T14:05:00.000Z",
    "role": "system", 
    "content": "Предмет 'Медальйон' переміщено з Інвентарю гравця в локацію 'Старий дуб'." 
  }
]
```

## 4. Управління та Конфлікти Пам'яті

Світ гри динамічний. Оскільки векторна БД зберігає всю історію, можуть виникати ситуації, коли знайдений старий спогад суперечить поточному стану (наприклад, пам'ять каже, що NPC живий, хоча його щойно вбили).

### 4.1. Незмінний літопис (Immutable Ledger)
Система **не видаляє** і не мутує старі вектори пам'яті. База працює як Event Sourcing (журнал подій). Усі записи зберігаються назавжди як історичні факти.

### 4.2. Вирішення конфліктів Майстром
Для запобігання логічним помилкам, застосовуються такі правила:
1. **Пріоритет жорстких станів:** Інструменти читання баз даних (F007-F014: стани NPC, інвентар гравця, погода) завжди мають найвищий пріоритет над пам'яттю. Якщо інструмент каже, що коваль мертвий, Майстер ігнорує спогади про те, що він живий.
2. **Хронологічний пріоритет:** Системний промпт Майстра містить правило: *"Якщо виникає суперечність між подіями в пам'яті, подія з новішим `world_time` завжди є актуальною правдою"*.
3. **Пріоритет активного контексту:** Події, які містяться в поточному нестисненому контексті (Останні Художні повідомлення та поточні Сухі логи), завжди перекривають будь-які факти, підтягнуті з Векторної БД.
