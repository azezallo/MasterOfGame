# Специфікація: Універсальний RAG-конвеєр (F018)

Цей документ описує систему автоматичного збору контексту (Auto-Prefetch) перед кожним ходом ШІ-Майстра. На відміну від цілеспрямованих інструментів, які Майстер викликає самостійно, Універсальний RAG працює на рівні бекенду і збагачує системний промпт релевантною інформацією *до* того, як модель почне генерувати відповідь.

## 1. Векторизація Динамічних Сутностей (Entity RAG)

Лор гри формується динамічно зусиллями самого Майстра. Тому ми не векторизуємо статичні файли, а додаємо семантичний пошук безпосередньо до ігрових сутностей у базі даних.

### 1.1. Додавання векторів до існуючих таблиць
Для реалізації семантичного пошуку ми розширюємо існуючі реляційні таблиці (через `sqlite-vec`), додаючи до них поле `embedding` (Float32Array).

Векторизуються наступні сутності:
1. **Локації (`locations`)**: 
   - *Що векторизується:* Назва локації, її опис та ключові особливості.
2. **Організації/Фракції (`organizations`)**: 
   - *Що векторизується:* Назва фракції, її публічний опис, цілі.
3. **NPC (`npcs`)**: 
   - *Що векторизується:* Ім'я NPC, публічний опис, роль.

*Примітка: Предмети (артефакти, `items`) **виключаються** з системи RAG, оскільки це створить забагато шуму (запит "Я дістаю меч" знайде всі мечі у грі).*

### 1.2. Синхронізація векторів (Автоматичне оновлення)
Векторизація відбувається повністю автоматично і приховано від ШІ-Майстра на стороні бекенду:
- Коли Майстер викликає інструменти створення (`create_npc`, `create_location`) або оновлення (`update_npc_public_profile`), бекенд бере текстові поля (ім'я + опис), пропускає їх через локальну embedding-модель (напр., `fastembed-js`) і записує отриманий вектор у БД разом із самою сутністю.
- Це гарантує, що база для RAG завжди на 100% синхронізована з поточним лором, який генерує Майстер.

## 2. Логіка Авто-підтягування (Auto-Prefetch)

Алгоритм RAG активується на Кроці 2 загального Агентного Циклу (Збірка контексту) — щоразу, коли гравець надсилає нове повідомлення.

### 2.1. Алгоритм пошуку
1. **Векторизація:** Репліка або дія гравця пропускається через локальну embedding-модель для створення вектора запиту.
2. **Паралельний запит:** Цей вектор одночасно порівнюється (через косинусну відстань `sqlite-vec`) із векторами у 4 таблицях: `semantic_history` (Історія), `locations` (Локації), `organizations` (Організації) та `npcs` (Персонажі).
3. **Гібридна фільтрація (Важливо):** Щоб уникнути семантичного шуму (напр., запит "купець" не повинен знайти купця на іншому континенті), пошук по таблиці `npcs` **жорстко фільтрується** за поточною локацією гравця. Якщо Майстру знадобиться далекий або відсутній NPC, він зможе знайти його цілеспрямовано через власні інструменти під час Re-Act циклу.

### 2.2. Форматування та Ліміти результатів
Для запобігання переповненню контекстного вікна Майстра (Token Explosion), діють суворі ліміти на кількість автоматично знайдених сутностей:
- **Історія (`semantic_history`)**: Максимум 3 найрелевантніші записи. Вставляються в промпт як текст із зазначенням ігрового часу (`world_time`).
- **NPC (`npcs`)**: Максимум 1-2 персонажі. Якщо знайдено, бекенд автоматично генерує їх опис через логіку `get_npc_context(id, 'DIALOG')` і додає як JSON.
- **Організації (`organizations`)**: Максимум 1 організація. Повертається як JSON через логіку `get_organization_details()`.
- **Локації (`locations`)**: Максимум 1 локація. Повертається як JSON у форматі `NAVIGATION_MODE`.

## 3. Ін'єкція Статичних Правил (Rules Engine)

Окрім динамічних сутностей та історії, гра керується набором глобальних правил (Базові правила механіки, Правила магії). Щоб мінімізувати розмір промпту, ці правила існують у двох форматах.

### 3.1. Формати правил
- **Спрощена версія (Short):** Стислий витяг (1-2 речення). **Завжди** присутня в базовому системному промпті Майстра. Нагадує йому про існування магії або механік та повідомляє, що він може дізнатися більше.
- **Повна версія (Full):** Детальний опис (ціни заклинань, формули шкоди, обмеження). Вставляється в промпт виключно тоді, коли дія гравця цього вимагає.

### 3.2. Алгоритм визначення наміру (Zero-Cost Intent Classification)
Бекенд визначає необхідність підключення "Повних правил" без додаткових викликів LLM, використовуючи вже згенерований на Кроці 2 вектор запиту гравця.
1. При старті сервера бекенд одноразово векторизує контрольні фрази-тригери:
   - Вектор Магії: `"заклинання, чари, магія, вогонь, мана, каст"`
   - Вектор Механік/Бою: `"атакую, б'ю, зброя, захищаюсь, шкода, битва"`
2. Коли приходить ввід гравця, його вектор порівнюється (cosine similarity) з цими контрольними векторами.
3. Якщо математична схожість перевищує заданий поріг (наприклад, `0.75`), бекенд автоматично замінює Спрощену версію на Повну перед викликом Майстра.
4. **Резервний механізм (Fallback):** Якщо алгоритм помилився і не підтягнув повні правила (наприклад, гравець описав магію дуже нестандартно), Майстер завжди може свідомо викликати інструмент `get_full_rules(category)` під час свого Re-Act циклу, оскільки Спрощена версія повідомляє про таку можливість.

## 4. Формування Системного Промпту (Prompt Assembly)

Зібрані на попередніх етапах дані повинні бути чітко структуровані, щоб ШІ-Майстер не плутав "об'єктивні правила" зі "спогадами" чи "поточним станом". 

Структура ін'єкції RAG у системний промпт виглядає наступним чином:

```xml
<WORLD_RULES>
  <!-- Сюди вставляється результат Етапу 3: Спрощені або Повні правила гри/магії -->
</WORLD_RULES>

<HARD_STATE>
  <!-- Жорсткий стан: Інвентар гравця, поточна погода, поточна локація -->
</HARD_STATE>

<RAG_CONTEXT>
  <!-- Сюди вставляється результат Етапу 2 -->
  <LORE>
    <!-- Автоматично знайдені Локації та Організації (JSON) -->
  </LORE>
  
  <RELEVANT_NPCS>
    <!-- Автоматично знайдені NPC на поточній локації у режимі DIALOG (JSON) -->
  </RELEVANT_NPCS>
  
  <PAST_MEMORIES>
    <!-- Найрелевантніші записи з semantic_history із зазначенням world_time -->
  </PAST_MEMORIES>
</RAG_CONTEXT>
```

Така XML-подібна структура гарантує, що Майстер сприйматиме ці блоки як окремі джерела правди. RAG-контекст завжди йде *після* жорстких станів, щоб у разі логічного конфлікту (згадка про живого NPC у PAST_MEMORIES, але відсутність його в HARD_STATE) Майстер пріоритезував HARD_STATE.
