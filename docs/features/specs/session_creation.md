# Специфікація фічі: Створення сесії (Session Creation)

## Огляд
Ця фіча дозволяє гравцеві створювати нові ігрові сесії. Це необхідно для того, щоб гравець міг почати нову гру або створити окремий світ зі своїм героєм.

## Роль гравця
- **Авторизований гравець**: Може створити нову сесію, ввівши назву гри та ім'я героя.

## Вимоги до даних (Session Metadata)
При створенні нової сесії бекенд повинен:
1. Згенерувати унікальний `session_id` (UUID).
2. Створити новий файл бази даних у директорії `saves/{player_id}/{session_id}.db`.
3. Ініціалізувати метадані для цієї сесії:
    - `game_name`: Назва, введена гравцем.
    - `character_name`: Ім'я героя, введене гравцем.
    - `created_at`: Поточний Unix timestamp.
    - `last_played_at`: Поточний Unix timestamp.

## Вимоги до API (Backend)

### 1. Створення сесії (`POST /sessions`)
- **Вхідні дані**: `game_name` (string), `character_name` (string).
- **Дії**:
    - Перевірити валідність вхідних даних (не порожні рядки, мінімальна довжина).
    - Згенерувати новий `session_id`.
    - Створити файл бази даних сесії.
    - Записати початкові метадані у базу даних або в систему зберігання метаданих.
- **Відповідь**: JSON з даними новоствореної сесії:
    ```json
    {
      "session_id": "uuid-xxx",
      "game_name": "...",
      "character_name": "...",
      "created_at": 1700000000,
      "last_played_at": 1700000000
    }
    ```

## Вимоги до UI (Frontend)

### 1. Екран створення сесії
- Форма створення сесії доступна через кнопку "Створити нову гру", яка розташована над таблицею вибору сесій на головній сторінці.
- Керування: При натисканні на кнопку форма відкривається у вигляді модального вікна (Popup).

### 2. Форма створення сесії (Popup)
- Поля: `gameName` (текст), `characterName` (текст).
- Кнопка: "Створити".
- **Розширюваність**: Форма повинна мати модульну структуру. Оскільки наразі не відомо, як багато інформації буде потрібно для старту гри, архітектура має дозволяти легке додавання нових полів у майбутньому без суттєвої переробки основної логіки запиту.
- **Валідація**: Використовувати Zod для перевірки довжини полів (від 1 до 255 символів) перед відправкою запиту.
- **Стани завантаження**: Під час виконання запиту модальне вікно повинно повністю перекриватися спіннером (Spinner) для відображення активного процесу.
- **Адаптивність**: На мобільних пристроях модальне вікно повинно розтягуватися на весь екран.

### 3. Поведінка після створення
- Після успішної відповіді від бекенду:
    - Автоматично перемкнути користувача на створену сесію через оновлення параметрів запиту в URL (наприклад, `?session_id=...`).

## Технічні деталі
- **Валідація**: Використовувати Zod для валідації даних форми (довжина 1-255 символів).
- **Обробка помилок**: Реалізувати відображення помилок аналогічно до форми авторизації.
- **UX**: Використовувати існуючі компоненти `Input`, `Button` та модальні вікна з дизайн-системи.
- **Навігація**: Використовувати оновлення URL параметрів для перемикання сесій.
