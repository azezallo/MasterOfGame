# Специфікація фічі: Система збереження сесій (Session Persistence)

## Опис
Система для збереження та завантаження стану гри гравця. Для забезпечення високої продуктивності, надійності та портативності використовуватиметься база даних **SQLite** (файлова БД). Кожна окрема ігрова сесія матиме свій власний файл бази даних.

## Цілі
- Забезпечити можливість перервати та відновити гру в будь-який момент.
- Гарантувати цілісність даних та атомарність операцій запису.
- Забезпечити портативність проєкту (один файл `.db` на одну сесію, що легко копіюється).
- Використовувати ефективні запити для пошуку та оновлення окремих параметрів без перепису всього стану.

## Технічні вимоги

### 1. Технологічний стек
- **База даних**: SQLite (через драйвер `better-sqlite3` або стандартний `sqlite3`).
- **Схема**: Використання таблиць для структурованих даних та JSON-полів для гнучких даних.

### 2. Структура зберігання
Дані зберігаються у папці `saves/` відносно кореня проєкту:
- `{player_id}/` — папка конкретного гравця.
- `{session_id}.db` — файл бази даних конкретної ігрової сесії.

### 3. Початкова структура таблиць (всередині кожного `.db`)
На початковому етапі передбачено такі таблиці:

#### Таблиця: `inventory`
Зберігає інформацію про предмети гравця.
- `id`: Унікальний ідентифікатор предмета.
- `name`: Назва предмета.
- `description`: Опис предмета (може бути великим текстом).
- `type`: Тип предмета (наприклад, 'weapon', 'potion', 'quest_item').

#### Таблиця: `npcs`
Зберігає інформацію про персонажів світу.
- `id`: Унікальний ідентифікатор персонажа.
- `name`: Ім'я персонажа.
- `description`: Загальний опис персонажа.
- `knowledge`: Дані про те, що персонаж знає (може бути JSON-об'єктом).
- `relationship`: Відношення до героя (числове значення або JSON-об'єкт).

#### Таблиця: `session_metadata`
Зберігає метадані поточної сесії.
- `last_save_timestamp`: Час останнього збереження.
- `current_time_block`: Поточний блок часу у світі.

### 4. Внутрішній сервіс (Internal Service)
Система реалізується як внутрішній сервіс у `master_of_game_API`, який забезпечує:
- Динамічне створення файлів `.db` при створенні нової сесії.
- Вибір правильного файлу БД на основі `session_id`.
- Інкапсуляцію запитів до БД.
- Обробку помилок бази даних.
- Мапінг між об'єктами коду та рядками БД.

## Критерії прийняття (Acceptance Criteria)
1. Система успішно створює новий файл `.db` при створенні нової сесії.
2. Можна створити новий предмет в інвентарі та успішно його відновити після перезапуску.
3. Можна створити NPC і зберегти його характеристики (ім'я, відношення тощо).
4. Використання SQLite дозволяє оновлювати окреме поле (наприклад, зміна імені NPC) без впливу на інші записи.
5. Використання відносних шляхів дозволяє запустити проєкт у будь-якій папці.
