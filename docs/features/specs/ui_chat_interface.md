# Специфікація: Інтерфейс Чату (F013)

Цей документ описує архітектуру та дизайн основного користувацького інтерфейсу гри — Чату. Оскільки ми дотримуємося філософії **Narrative-First UI**, чат є єдиним вікном взаємодії гравця зі світом.

## 1. Базовий Лейаут та Слоти Розширення (Core Layout)

Для забезпечення масштабованості інтерфейсу в майбутньому (коли з'являться інструменти візуалізації), ми використовуємо **3-колонковий макет** з прихованими бічними панелями.

### 1.1. Структура макета
- **Ліва панель (Left Sidebar):** "Слот" для технічної інформації про гравця. У майбутньому тут розміщуватиметься Інвентар, Стан персонажа (HP, мани) та Міні-карта.
- **Центральна панель (Main Chat):** Головна зона гри. Завжди видима. Містить історію повідомлень та зону вводу.
- **Права панель (Right Sidebar):** "Слот" для енциклопедичної інформації. У майбутньому тут відображатимуться деталі про NPC (з якими йде діалог), Локації та Організації.

### 1.2. Адаптивність
- **Desktop:** Центральна панель займає основний простір. Бічні панелі можна розгортати (Toggle) або закріплювати.
- **Mobile:** Видима лише Центральна панель чату. Бічні панелі ховаються за кнопками-бургер меню (або свайпами) і відкриваються як Overlay. На початковому етапі (MVP) ці панелі просто не рендеряться.

## 2. Дизайн Повідомлень (Message Bubbles)

Комунікація у чаті суворо розділена візуально, щоб гравець миттєво зчитував контекст.

### 2.1. Типи повідомлень
1. **Повідомлення Гравця (Player Bubble):**
   - *Вирівнювання:* По правому краю (як у стандартних месенджерах).
   - *Стиль:* Яскравий акцентний колір фону.
   - *Зміст:* Заявлені дії гравця ("Я дістаю меч і йду в темряву").
2. **Відповідь Майстра (Master Narrative):**
   - *Вирівнювання:* По лівому краю.
   - *Стиль:* Темний преміальний фон, красива типографіка (з підтримкою Markdown для виділення жирним або курсивом важливих речей).
   - *Зміст:* Опис світу, наслідки дій, репліки NPC. Усе, що стається у грі (навіть отримання предметів чи поранення), описується тут *виключно художнім текстом*.
3. **Системні Сповіщення (System Notifications):**
   - *Вирівнювання:* По центру (дрібний нейтральний текст, можливо з напівпрозорим фоном).
   - *Зміст:* **Виключно неігрові технічні події.** Наприклад: "З'єднання з сервером втрачено", "Виконується стиснення історії".
   - *Заборонено:* Жодних ігрових сповіщень типу "Збережено", "Отримано 5 монет" чи "HP -10". Уся ігрова інформація лежить у наративі Майстра або жорстких станах БД.

У чаті немає кнопок для виконання ігрових действий (напр., "Атакувати", "Забрати лут", "Погодитись"). Гравець повинен *написати* про свій намір у поле вводу. Це фундаментальне правило Narrative-First UI.

## 3. Зона Вводу та UX Очікування (Input & Loading States)

Оскільки генерація відповіді (особливо на локальних LLM) та виклики інструментів Майстром можуть займати значний час, критично важливо забезпечити гравця зворотним зв'язком.

### 3.1. Поведінка поля вводу
- **Багаторядковість:** Поле вводу (Textarea) автоматично розширюється залежно від кількості тексту.
- **Гарячі клавіші:** `Enter` — відправити повідомлення, `Shift + Enter` — перехід на новий рядок.
- **Блокування:** Щойно гравець відправляє повідомлення, поле вводу блокується (Disabled), поки Майстер не завершить свою відповідь. Це запобігає розсинхронізації станів через спам повідомленнями.

### 3.2. Прозорість думок Майстра (Intermediate Statuses)
Замість статичного індикатора завантаження, гравець бачить динамічний процес роботи Майстра.
У чаті з'являється "бульбашка очікування" (Loader), під якою дрібним шрифтом оновлюється поточний статус бекенду:
- *"Збір спогадів..."* (Етап RAG)
- *"Перевірка мапи..."* (Виклик інструменту `read_map`)
- *"Майстер обмірковує наслідки..."* (LLM генерує фінальну відповідь)

## 4. Інтеграція Даних (Data Flow)

Щоб реалізувати динамічне оновлення статусів (Етап 3) та можливий стрімінг самої відповіді Майстра, класичний HTTP-запит (де клієнт чекає 15 секунд на одну велику відповідь) не підходить.

### 4.1. Short Polling (Оптимізація для локального сервера)
### 4.1. Short Polling (Оптимізація для локального сервера)
Оскільки гра орієнтована на локальний запуск, і гра є синхронною (один глобальний стан очікування для всієї сесії), використання WebSockets є надмірним. Натомість ми використовуємо **Short Polling** для перевірки єдиного стану гри:

1. **Ініціалізація:** Гравець надсилає `POST /chat/message` зі своєю дією. Бекенд фіксує, що гра перейшла у стан обробки (PROCESSING) і миттєво повертає успіх `202 Accepted`.
2. **Опитування (Polling):** Поки поле вводу заблоковане, фронтенд кожні 200–500 мілісекунд надсилає легкий запит `GET /game/status`.
3. **Проміжні відповіді (Enum для i18n):** Бекенд відповідає JSON-ом із поточним кроком у форматі Enum. Це дозволяє легко локалізувати UI (i18n):
   `{"status": "GATHERING_MEMORY", "is_ready": false}`
   *(Можливі статуси: `GATHERING_MEMORY`, `READING_MAP`, `GENERATING_NARRATIVE` тощо)*
4. **Завершення:** Коли Майстер згенерував відповідь, стан гри змінюється, і наступний GET-запит повертає:
   `{"status": "IDLE", "is_ready": true, "message": "Фінальний художній текст"}`
5. Після отримання фінального повідомлення, фронтенд рендерить його у чат, розблоковує поле вводу **та ініціює фонове оновлення стану всіх UI-компонентів** (Інвентар, Карта, Характеристики гравця), оскільки Майстер міг змінити їх протягом свого ходу.

Цей підхід знімає необхідність підтримувати постійні з'єднання і ідеально підходить для нашої локальної архітектури.
