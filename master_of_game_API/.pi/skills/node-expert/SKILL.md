# Node.js Expert Skill

Цей скіл надає мені спеціалізовані інструкції для розробки бекенду в проєкті Master of Game. Коли цей скіл активний, я суворо дотримуюся архітектурних принципів проєкту та методології покрокового виконання завдань.

## Workflow & Execution Rules

### 1. Покрокове виконання (Strict Stage Adherence)
- **Виконуй лише один етап одночасно**: Я маю працювати виключно над тим етапом, який зараз визначений у плані. Не намагайся виконати наступний етап, поки поточний не буде повністю завершений і перевірений.
- **Пауза після кожного етапу**: Після завершення кожного етапу я маю зупинитися і дочекатися підтвердження від користувача або наступної команди для переходу до наступного кроку.

### 2. Звітність про виконання (Reporting)
Після завершення кожного етапу, я повинен надати структурований звіт, що включає:
- **Виконані дії**: Список створених або змінених файлів, виконаних команд.
- **Ключові зміни**: Короткий опис внесених технічних змін (наприклад, "реалізовано репозиторій для інвентарю", "створено Zod-схеми для NPC").
- **Стан системи**: Чи успішно пройшли тести (якщо проводилися) та чи є будь-які залишкові зауваження чи проблеми.
- **Наступний крок**: Нагадування про те, який етап планується наступним.

## Архітектурна модель: Layered Architecture (Шарова архітектура)

Для забезпечення масштабованості та чистоти коду ми використовуємо чотири основних шари:

### 1. Routing Layer (Controllers)
- **Роль**: Обробка вхідних HTTP-запитів.
- **Відповідальність**:
    - Витягування параметрів запиту (body, params, query).
    - Валідація вхідних даних за допомогою **Zod**.
    - Виклик відповідного сервісу.
    - Повернення стандартної відповіді (Success/Error).
- **Заборонено**: Містити будь-яку бізнес-логіку або прямі запити до бази даних.

### 2. Service Layer (Business Logic)
- **Роль**: Серце гри.
- **Відповідальність**:
    - Виконання ігрових правил (магія, бої, соціальні взаємодії).
    - Обробка логіки стану світу.
    - Координація дій між різними репозиторіями.
- **Заборонено**: Знати про деталі транспорту (HTTP, WebSockets) або деталі реалізації бази даних.

### 3. Data Access Layer (Repositories)
- **Роль**: Абстракція доступу до даних.
- **Відповідальність**:
    - Виконання запитів до бази даних (наприклад, SQLite).
    - Мапінг результатів БД у типи TypeScript (DTO).
    - Гарантування атомарності операцій запису.
- **Заборонено**: Містити бізнес-логіку (наприклад, розрахунок шкоди або мані).

### 4. Domain Models & Types
- **Роль**: Опис сутностей світу.
- **Відповідальність**:
    - Інтерфейси TypeScript для всіх об'єктів.
    - Схеми валідації даних (Zod).

## Best Practices

### 1. Type Safety & Validation
- Використання сурого режиму TypeScript (`strict: true`).
- Валідація вхідних даних на рівні контролерів за допомогою **Zod**.

### 2. Error Handling
- Централізована обробка помилок через Middleware.
- Використання спеціальних класів помилок (`AppError`, `ValidationError`, `DatabaseError`).
- Відсутність дублювання блоків `try/catch` у контролерах (обробка на рівні сервісів/репозиторіїв).

### 3. Configuration & Environment
- Використання `.env` для всіх конфігураційних параметрів.
- Централізований об'єкт конфігурації для зручного доступу до налаштувань системи.

### 4. Logging & Observability
- Використання структурованого логування (Pino/Winston).
- Логування ключових подій (створення сесій, критичні помилки БД, дії гравців).

### 5. Database Management
- Атомічний запис даних.
- Використання відносних шляхів для забезпечення портативності бази даних.
- Використання JSON-полів у SQLite для зберігання гнучких, неструктурованих даних.
