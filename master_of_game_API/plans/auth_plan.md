# План розробки бекенд-частини: Авторизація та Реєстрація (Auth)

## Огляд
Реалізація системи безпечної реєстрації, входу та управління сесіями гравців. Використовується окрема база даних `saves/users.db` та система куків для збереження стану авторизації.

## Етапи виконання

### Етап 1: Підготовка бази даних та інфраструктури
- [x] Створити файл бази даних `saves/users.db`.
- [x] Виконати міграції для створення таблиць:
    - `players` (login, password_hash).
    - `sessions` (session_id, login, expires_at).
- [x] Налаштувати конфігурацію в `.env` для терміну дії сесії та шляхів до БД.
- [x] Створити базові типи даних (TypeScript interfaces) для `Player`, `Session` та `AuthResponse`.

### Етап 2: Створення сервісного шару (AuthService)
- [x] Реалізувати сервіс хешування паролів (використовуючи стандартні засоби Node.js).
- [x] Реалізувати `AuthService`:
    - Метод `register(login, password)`: перевірка унікальності, хешування, запис у БД.
    - Метод `login(login, password)`: перевірка пароля, генерація `session_id`, запис у таблицю сесій.
    - Метод `getSession(session_id)`: перевірка терміну дії, отримання даних гравця.
- [x] Реалізувати сервіс генерації випадкових токенів для сесій.

### Етап 3: Реалізація API ендпоінтів
- [x] Створити контролери для:
    - `POST /auth/register`
    - `POST /auth/login`
    - `GET /auth/me`
- [x] Налаштувати роутинг для цих ендпоінтів.
- [x] Інтегрувати валідацію вхідних даних за допомогою **Zod**.

### Етап 4: Middleware та безпека
- [x] Створити Middleware для перевірки сесії з куки.
- [x] Інтегрувати Middleware у захищені маршрути.
- [x] Налаштувати відповідні заголовки куків (`HttpOnly`, `SameSite=Lax`).
- [x] Провести тестування всіх сценаріїв (успішний вхід, помилка пароля, застаріла сесія).

## Критерії прийняття (Acceptance Criteria)
1. База даних `users.db` створюється автоматично при першому запуску.
2. Реєстрація працює коректно: паролі зберігаються лише у хешованому вигляді.
3. Авторизація повертає куку з `session_id`.
4. Ендпоінт `/auth/me` повертає дані тільки для валідиних сесій.
5. Всі відповіді відповідають формату, описаному в специфікації `docs/features/specs/auth.md`.
