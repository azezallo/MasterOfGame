# План розробки бекенд-частини: Вибір сесії (Session Selection)

## Огляд
Реалізація функціоналу перегляду доступних ігрових сесій гравця. Бекенд повинен сканувати файли бази даних сесій, збирати їхні метадані та надавати їх фронтенду для відображення.

## Етапи виконання

### Етап 1: Моделі даних та базові сервіси (Виконано)
- [x] Розширити об'єкт `SessionMetadata` у системі збереження даних.
- [x] Створити сервіс `SessionMetadataService` для:
    - Отримання метаданих з БД (якщо вони вже існують).
    - Створення/оновлення метаданих для нової сесії.
- [x] Реалізувати функціонал отримання списку доступних сесій для гравця (`/saves/{player_id}/`).
- [x] Реалізувати логіку оновлення `last_played_at` при кожному успішному запиті до ігрової сесії.

### Етап 2: Реалізація API ендпоінтів
- [ ] Створити ендпоінт `GET /sessions`:
    - Витягувати `player_id` або ідентифікатор гравця з авторизаційних даних.
    - Сканувати папку `saves/{player_id}/` для пошуку `.db` файлів.
    - Формувати відповідь з даними `SessionMetadata` для кожного файлу.
- [ ] Інтегрувати валідацію доступу (тільки авторизовані гравці можуть бачити свої сесії).

### Етап 3: Інтеграція та тестування
- [ ] Перевірити коректність форматування дат (`created_at`, `last_played_at`) у відповіді.
- [ ] Перевірити оновлення `last_played_at` під час імітації ігрових дій.
- [ ] Виконати інтеграційне тестування запиту `/sessions`.

## Критерії прийняття (Acceptance Criteria)
1. Бекенд успішно повертає список усіх сесій гравця у форматі JSON.
2. Кожна сесія містить назву гри, ім'я героя, дату створення та дату останньої гри.
3. Поле `last_played_at` оновлюється автоматично під час взаємодії з сесією.
4. Доступ до списку сесій обмежений лише авторизованими користувачами.
5. Відповідність JSON-структурі специфікації `docs/features/specs/session_selection.md`.
