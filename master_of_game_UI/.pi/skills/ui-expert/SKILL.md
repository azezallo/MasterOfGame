# UI Expert Skill

Цей скіл надає мені спеціалізовані інструкції для розробки фронтенд-частини у проєкті Master of Game. Коли цей скіл активний, я суворо дотримуюся архітектурних принципів проєкту та методології покрокового виконання завдань.

## Workflow & Execution Rules

### 1. Покрокове виконання (Strict Stage Adherence)
- **Виконуй лише один етап одночасно**: Я маю працювати виключно над тим етапом, який зараз визначений у плані. Не намагайся виконати наступний етап, поки поточний не буде повністю завершений і перевірений.
- **Пауза після кожного етапу**: Після завершення кожного етапу я маю зупинитися і дочекатися підтвердження від користувача або наступної команди для переходу до наступного кроку.

### 2. Звітність про виконання (Reporting)
Після завершення кожного етапу, я повинен надати структурований звіт, що включає:
- **Виконані дії**: Список створених або змінених файлів, виконаних команд.
- **Ключові зміни**: Короткий опис внесених технічних змін (наприклад, "реалізовано компоненти кнопок", "створено систему повідомлень").
- **Стан системи**: Чи успішно пройшли тести (якщо проводилися) та чи є будь-які залишкові зауваження чи проблеми.
- **Наступний крок**: Нагадування про те, який етап планується наступним.

## Архітектурна модель: Feature-Based Architecture

Для забезпечення масштабованості та чистоти коду ми використовуємо підхід, де код організований навколо фіч:

### 1. Feature-Based Structure
- **src/features/**: Ізольовані бізнес-модулі.
- **src/components/ui/**: Базові UI-компоненти загального призначення.
- **src/hooks/**: Глобальні перевикористовуювані хуки.
- **utils/** — Допоміжні чисті функції (форматування дат, математичні розрахунки)
- **services/** — Базовий API-клієнт, робота з LocalStorage, конфігурація WebSockets
- **src/services/**: Базовий API-клієнт та робота з LocalStorage.

### 2. Шари всередині бізнес-модуля (Feature Layers)
Кожна фіча повинна бути розділена на чотири шари:
- **Presentation Layer (UI Components)**: Виключно відображення інтерфейсу. Не містить бізнес-логіки або прямих запитів до API.
- **Logic Layer (Custom Hooks)**: "Мозок" фічі. Керує станом, обробкою подій та взаємодією з сервісами.
- **API & Data Access Layer (Services / Client)**: Абстракція мережевих запитів та мапінг даних (DTO -> Domain Model).
- **Domain Models & Types**: Опис сутностей, TypeScript інтерфейси та Zod-схеми валідації.

## Технічні вимоги та Стилістика

### 1. Стилізація (CSS Modules)
- Використовувати **CSS Modules** для інкапсуляції стилів кожного компонента.
- **Темна фантастика (Dark Fantasy)**:
    - **Пергамент**: Текстури та кольори для зонуювання тексту.
    - **Залізо та Вогонь**: Елементи керування (кнопки, рамки).
    - **Золото**: Акценти для важливих елементів та заголовків.

### 2. Інтеграція Дизайн-Системи (UI Components)
- **Обов'язкове використання**: Усі базові UI-елементи (кнопки, інпути, селекти, чекбокси, радіо-кнопки, діалоги) повинні братися з `src/components/ui/`.
- **Заборона на дублювання**: Заборонено створювати власні стилі або компоненти для стандартних елементів інтерфейсу, якщо вони вже існують у дизайн-системі.
- **Адаптивність**: Усі компоненти повинні бути адаптовані під мобільні екрани.
- **Loading States**: Обов'язкова візуалізація станів завантаження (Spinners/Skeletons).
- **Типобезпека**: Суворий режим TypeScript та валідація даних за допомогою **Zod**.

## Best Practices

### 1. Чистота компонентів
- Компоненти презентації повинні бути "дурними" (Dumb Components).
- Виносити будь-яку складну логіку у власні хуки.

### 2. Робота з даними
- Використовувати мапінг даних з бекенду у зручні для фронтенду моделі перед передачею в компоненти.
