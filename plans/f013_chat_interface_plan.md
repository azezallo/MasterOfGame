# План реалізації F013: Інтерфейс Чату (Спрощена версія)

Цей документ описує створення специфікації для базового UI чату, який є серцем гри (згідно з принципом Narrative-First UI). На цьому етапі ми створюємо мінімально життєздатну версію (MVP), але закладаємо архітектурні "слоти" для майбутніх розширень.

## Етапи реалізації специфікації (`ui_chat_interface.md`):

- `[x]` **Етап 1: Базовий Лейаут та Слоти Розширення (Core Layout)**
  - Розбиття екрану на зони: Головна зона чату (по центру), Зона вводу (внизу), та зарезервовані приховані панелі (Left Sidebar для інвентарю/карти, Right Sidebar для лору/NPC).
  - Наразі бічні панелі будуть порожніми або мінімізованими, але структура React-компонентів має підтримувати їх вставку пізніше.

- `[x]` **Етап 2: Дизайн Повідомлень (Message Bubbles)**
  - Візуальне розмежування типів повідомлень:
    1. Репліки гравця.
    2. Відповіді Майстра (художній текст).
    3. Системні сповіщення (виключно технічні події не зі світу гри: "Розірвано підключення", "Стиснення контексту завершено"). Жодних повідомлень типу "Отримано предмет" — усе це вирішується наративно!
  - Відмова від кнопок дій (ніяких кнопок "Атакувати" в самому чаті).

- `[x]` **Етап 3: Зона Вводу та UX очікування (Input & Loading States)**
  - Поведінка поля вводу (Enter - відправити, Shift+Enter - новий рядок).
  - Оскільки Агентний Цикл Майстра може займати від 5 до 15 секунд (пошук RAG, виклик інструментів, генерація), нам потрібен чіткий індикатор очікування (наприклад, анімація "Майстер обмірковує хід...").

- `[x]` **Етап 4: Інтеграція Даних (Data Flow)**
  - Як фронтенд отримуватиме повідомлення? Враховуючи тривалий час відповіді, чи використовуємо ми звичайний HTTP-запит (і чекаємо), чи WebSocket/Server-Sent Events (SSE) для того, щоб Майстер міг частинами відправляти результати?
